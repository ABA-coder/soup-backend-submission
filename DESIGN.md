# Design before code

**Scope:** one host, one SQLite database on a local durable filesystem, one HTTP API and four or more independent worker processes. A job emulates training by waiting and then writing one result row. This is not a GPU scheduler. SQLite keeps the exercise small and makes the result and job state share a transaction; its single writer and single host are deliberate limits. Use rollback journal mode `DELETE`, `synchronous=FULL`, foreign keys, a busy timeout, and explicit short `BEGIN IMMEDIATE` write transactions. No transaction spans simulated training. WAL is not needed for this prototype; portable system SQLite versions may lack the WAL-reset fix.

**Accept and identify:** `POST /jobs` requires a permanent, globally unique idempotency key. Normalize and store the validated payload. In one write transaction, either insert a queued job or return the existing job. The same key with a different normalized payload returns 409. A lost HTTP response can be retried without creating another job. No deletion or key expiry is implemented. List uses increasing integer IDs and a captured upper bound for stable keyset pagination (membership is stable; status can change).

**Claim and recover:** acquire SQLite's writer lock before reading candidates. Prefer an expired running job, then the oldest queued job. Increment its fencing token, increment its attempt counter, record its worker identity and database-derived lease deadline, and insert an attempt record in the same transaction. Competing claims serialize. Workers renew at approximately a third of the lease, using database time and a conditional update on ID, running state, worker identity, token, and an unexpired lease. An expired worker cannot renew. No separate reaper is required: the next claimant reassigns an expired job. Liveness assumes an available database, at least one eventually healthy worker, and finite failures. Reassignment keeps the observable state running.

**Complete and fence:** the durable emulated side effect is a result row with outcome `succeeded` or `failed`. After obtaining the writer lock, require the current running state, matching worker and fencing token, and an unexpired lease. Insert the effect and make the terminal state change in the same transaction. The result has a unique job ID as a second line of defense; duplicate insertion is an error, never silently ignored. A killed process commits both changes or neither. Retrying an old completion cannot add an effect. A lease that expires during a transaction cannot let a competing owner commit concurrently because the writer lock serializes them. Unexpected worker errors leave the lease for recovery; deterministic simulated training failure is terminal and has one failed-result row.

**Cancel:** cancellation and completion contend for the same writer lock. If cancellation wins, queued or running becomes cancelled immediately, ownership is cleared, and the token is incremented. That worker stops on its next renewal or completion check; sleeping/CPU work may briefly continue, but it cannot publish a result. If completion wins, cancel returns 409 with the terminal status. Repeated cancellation is 200. Cancelled jobs have zero effects; succeeded/failed jobs have exactly one matching effect. Cancellation does not promise interruption of an arbitrary external program.

**Guarantee and limits:** attempts are at least once; the local, transactional result effect is exactly once for executed terminal jobs and zero for cancelled jobs. It is not exactly-once computation or an exactly-once remote API/file write. A future external effect needs its own transactional/idempotent protocol. Database time is read after acquiring the lock; worker wall clocks do not set leases. All SQLite processes share the host clock. A host clock jump can delay recovery or cause an early reclaim; fencing preserves result safety but does not bound recovery under arbitrary clock changes. No HA, authentication, per-tenant keys, admission control, metrics backend, backup restoration proof, or claim of sustained 100 RPS readiness.

**Evidence plan:** race claims, retries and cancel/complete; test expired zombies and clock jumps; kill a process between effect insertion and state update; run 10,000 HTTP-created jobs with eight processes, repeat POSTs and cancellation, and random hard kills about every two seconds. Independently reconcile every input key, recorded response, attempt, effect, and terminal state. Preserve every run's raw logs, including failures. A finite local test cannot prove all schedules or power-loss durability. Initial verdict: **DON'T SHIP** until production-specific evidence and operating controls exist.
